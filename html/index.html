多清晰度直播（ABR）
完整实现流程

从「一路源流」到「用户自己挑 720p / 1080p / 2K / 4K」，中间到底发生了什么、要不要推多路、 HLS 是怎么把这些路串起来的 —— 下面这张全链路图和 6 个必查的坑，一次讲透。

核心结论：推 1 路，服务器转出 N 路 索引文件：master.m3u8 播放器：hls.js 自动 + 手动
01

先回答你最关心的：是不是要推多路？

你的直觉方向是对的 —— 最终确实会有多路流给用户选。但这多路流不该由你的推流端推出来， 而是应该由服务器（或转码器）从一路源流转码出来。这是两种做法，差别很大：

做法 A：推流端推多路（不推荐）

香橙派上同时压缩 720p、1080p、2K、4K 四条流再推上去。结果就是：上行带宽翻倍、CPU 直接跑满、画面掉帧。 香橙派这种 ARM 小设备根本扛不住 4K 编码，属于用最弱的机器干最重的活。

做法 B：推 1 路，服务器转多路（推荐）

香橙派只推一路原始流（比如 1080p 或直接摄像头原画），到了服务器再用 FFmpeg 一次性转出多档分辨率。 推流端只干一次活，转码交给更强的机器做。

一句话总结： 你说的「推多路」在物理上确实存在，但它发生在转码环节，而不是采集推流环节。 你需要的技术名字叫 ABR（自适应码率 / Adaptive Bitrate）， 它的载体就是 HLS 的 Master Playlist（主播放列表）。

02

完整链路：从摄像头到用户选清晰度

整条链路一共 6 个环节，前 2 步是你已经在做的，后面 4 步才是「多清晰度」的关键。

1

采集 + 编码（香橙派 / 摄像头）

摄像头采集画面，本地压成 一路 H.264，音频一路 AAC。这一路就是"母带"。

1 路视频 1 路音频
2

推流到服务器（RTMP / SRT）

香橙派把这一路流推给你的服务器（MediaMTX / SRS / Nginx-RTMP）。只推一路，省上行带宽。

3

转码：一路变多路 ★关键

用 FFmpeg（软编或硬编）把这一路母带同时转出 720p / 1080p / 2K / 4K， 每档用不同的码率。转码是 1→N，不是采集端 1→N。

720p · ~2.5 Mbps 1080p · ~5 Mbps 2K · ~10 Mbps 4K · ~20 Mbps
4

切片 + 生成各级清单 ★关键

每一路都被切成固定时长的小分片（.ts 或 .m4s）， 并各自生成一份该档位的播放清单（media playlist，例如 720p/index.m3u8）。

5

汇总成 Master Playlist（总菜单）★关键

生成一个 master.m3u8， 里面不存分片，只记录"有哪几档清晰度、每档多少带宽、多少分辨率、去哪个子清单取"。 这就是把多路"结合起来"的那份文件。

6

播放器：自动切换 + 用户手选

播放器只请求 master.m3u8， 读到所有档位后：默认按网速自动升降档（ABR），同时把档位列表丢给"清晰度"按钮，让用户手动锁定。

03

"路"是怎么被结合起来的：三层结构

HLS 多码率是三层嵌套，理解这三层，你就理解了全部：

第 1 层 · 总入口
master.m3u8

列出所有清晰度档位（带宽 / 分辨率 / 编码 / 子清单地址）。用户和播放器只看这一份。

第 2 层 · 每档清单
720p/index.m3u8

描述本档位有哪些分片、时长多少、下一个分片去哪取。每档一份。

第 3 层 · 分片
seg_00001.ts

真正的音视频数据，小文件，可被 CDN 缓存，播放器一个个拉。

# master.m3u8 —— 你手写的（或 FFmpeg 自动生成的）总菜单，长这样： #EXTM3U #EXT-X-VERSION:3 # 720p 档位：带宽 2.5Mbps，分辨率 1280x720 #EXT-X-STREAM-INF:BANDWIDTH=2500000,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2" 720p/index.m3u8 # 1080p 档位：带宽 5Mbps #EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080,CODECS="avc1.640028,mp4a.40.2" 1080p/index.m3u8 # 2K 档位：带宽 10Mbps #EXT-X-STREAM-INF:BANDWIDTH=10000000,RESOLUTION=2560x1440,CODECS="avc1.640033,mp4a.40.2" 2k/index.m3u8 # 4K 档位：带宽 20Mbps #EXT-X-STREAM-INF:BANDWIDTH=20000000,RESOLUTION=3840x2160,CODECS="avc1.640034,mp4a.40.2" 4k/index.m3u8

划重点：把多路"结合"起来，靠的就是这份 master.m3u8 —— 它是纯文本索引文件，不是视频。 播放器拿到它，就知道"有 4 档可选，每档去哪拿"，用户点"1080p"时播放器就切到第 2 条子清单继续拉。

04

一条 FFmpeg 命令，转出 N 路 + 自动生成总菜单

不用手写 master.m3u8。FFmpeg 的 -var_stream_map 会一边转码、一边切片、一边把 master.m3u8 生成好：

ffmpeg -re -i rtmp://your-server/live/source \ -filter_complex \ "[0:v]split=2[v1][v2]; \ [v1]scale=1280:720[v1out]; \ [v2]scale=1920:1080[v2out]; \ [0:a]asplit=2[a1][a2]" \ # 2 档视频，各自的码率 -map "[v1out]" -c:v:0 libx264 -b:v:0 2500k -maxrate:v:0 2675k -bufsize:v:0 5000k \ -map "[v2out]" -c:v:1 libx264 -b:v:1 5000k -maxrate:v:1 5350k -bufsize:v:1 10000k \ # 音频编码 -map "[a1]" -c:a:0 aac -b:a 128k -ar 48000 \ -map "[a2]" -c:a:1 aac -b:a 128k -ar 48000 \ # 禁用b帧，关键帧对齐（GOP 必须一致，否则切换花屏） -bf 0 -g 30 -keyint_min 30 \ # 固定帧率 -r 30 -sc_threshold 0 \ # HLS 切片参数，每个切片3秒，列表固定20个切片 -f hls -hls_time 3 -hls_list_size 20 \ # HLS 切片过期自动删除 -hls_flags delete_segments+independent_segments \ # HLS 过期切片保留最近的10个，防止过度删除 -hls_delete_threshold 10 \ # name 将自动填充占位符 %v -var_stream_map "v:0,a:0,name:720p v:1,a:1,name:1080p" \ -master_pl_name master.m3u8 \ -hls_segment_filename "out/%v/seg_%03d.ts" \ "out/%v/index.m3u8"
-var_stream_map

把"视频第几路 + 音频第几路"打包成一个变体（variant）。v:0,a:0 表示变体 0 = 第 1 路视频 + 第 1 路音频。

-master_pl_name

指定总菜单文件名。生成后，播放器只需要这一份地址即可。

%v

变体编号占位符，用来把不同清晰度分到不同子目录（720p / 1080p …）。

-g 30

GOP 长度（每 30 帧一个关键帧）。所有档位必须一致，否则切清晰度会花屏。

05

播放器端：用户怎么"选"，播放器怎么"自动切"

网页端用 hls.js。它俩件事一次搞定：默认自动 ABR，同时把档位列表交给你做"清晰度按钮"。 点下面按钮体验一下"手动锁定清晰度"的效果：

清晰度选择（模拟播放器 UI）
hls.currentLevel = -1

当前为自动模式：hls.js 会根据用户实时网速在 720p ~ 4K 之间自动升降档。

// 前端核心逻辑（hls.js） const video = document.getElementById('video'); const hls = new Hls(); hls.loadSource('你的域名/live/master.m3u8'); // 只拉总菜单 hls.attachMedia(video); // 1) 默认自动 ABR hls.currentLevel = -1; // 2) 手动切清晰度 // -1 = 自动；0 = 最低档；数字越大越清晰（按 master.m3u8 里的顺序） function setQuality(level) { hls.currentLevel = level; } // 3) 把档位列表渲染成"清晰度"按钮 hls.on(Hls.Events.MANIFEST_PARSED, (e, data) => { data.levels.forEach((lv, i) => { console.log(i, lv.width + 'x' + lv.height, Math.round(lv.bitrate / 1000) + ' kbps'); }); });
自动切换（ABR）

hls.js 统计每个分片的下载速度，对比 master.m3u8 里各档的 BANDWIDTH，网差自动降档、网好自动升档。 用户什么都不用管。

手动锁定

设置 hls.currentLevel = N 即锁定某一档（-1 恢复自动）。 产品上建议同时提供"自动 + 手动"两个入口。

先认清"2K / 4K 直播"的带宽与成本现实

清晰度越高，码率越高，对服务器出口带宽和观众网络的考验越大。下是 H.264 下各档位的典型推荐码率：

现实提醒：1 路 4K 观众每秒要吃掉约 20 Mbps。如果同时有 100 人在看 4K， 就是 2 Gbps 出口带宽。所以真实平台一般会： ① 用 H.265 省 30%~50% 带宽；② 上 CDN 分发；③ 4K 只当作"可选高码率档"，不默认开启。

07

六个必查的坑（多码率专属）

① 关键帧（GOP）没对齐

各档位的 I 帧时间点不一致，切清晰度瞬间会花屏 / 卡顿。所有档位必须用同一个 -g 值，并加 -sc_threshold 0。

② BANDWIDTH 数值乱写

master.m3u8 里带宽值和真实码率差太多，ABR 判断会完全错乱。填接近真实码率的值，别凭感觉估。

③ 音频每档重编一遍

必须，不能共用一路音频。

④ 分片时长不统一

各档 -hls_time 必须一致，分片边界要对齐，否则切换时对不上时间轴。直播建议 2~4 秒。

⑤ 缺少 H.264 兜底档

如果全用 H.265，部分浏览器直接解不了。至少保留一路 H.264 低码率兜底。

⑥ 直播清单保留策略不一致

各档 -hls_list_size 保留的分片数最好一致，否则切换后要的分片已被淘汰，直接断流。

08

落到你的香橙派 + MediaMTX 场景

关键事实：MediaMTX 自己不做转码。 所以"多清晰度"这件事，必须由外部的 FFmpeg 来完成 —— 和前面讲的逻辑一样， 让 FFmpeg 从 MediaMTX 拉一路源，转出多档 HLS，再交给 Web 服务器 / CDN 分发。

而香橙派的算力限制，决定了你本地转 4K 几乎不现实。给你三档务实建议：

方案 A（最务实）：本地只做 720p + 1080p 两档

香橙派推 1 路原画到 MediaMTX；在同一台服务器（哪怕也是小机器）上跑上面的 FFmpeg 命令，只转 720p + 1080p。 两档已经覆盖绝大多数用户的网速，CPU 压力可控。2K/4K 先不上。

方案 B：需要 4K，就把转码搬到大机器 / 云上

香橙派只负责"推一路高质量原流"，转码交给带 GPU（NVENC）或独立算力的服务器 / 云转码服务。 这和阿里云、腾讯云"直播转码"是同一个套路 —— 源流进、多档 HLS 出。

方案 C：只是想"能选"，不必真 4K

很多平台标着"4K"其实只是把 1080p 放大。你可以先做 480p / 720p / 1080p 三档， 前端 UI 照样给用户"清晰度"按钮，先跑通 ABR 全链路，再按需加档。

# 在你的服务器上跑：从 MediaMTX 拉源 → 转两档 HLS → 输出到 Web 目录
# 在香橙派推流到 MediaMTX 的 live/source ffmpeg -re -i rtsp://localhost:8554/live/source \ -filter_complex \ "[0:v]split=2[v1][v2]; \ [v1]scale=640:360[v1out]; \ [v2]scale=1280:720[v2out]; \ [0:a]asplit=2[a1][a2]" \ -map "[v1out]" -c:v:0 libx264 -b:v:0 1000k -maxrate:v:0 1000k -bufsize:v:0 2000k \ -map "[v2out]" -c:v:1 libx264 -b:v:1 2000k -maxrate:v:1 2000k -bufsize:v:1 4000k \ -map "[a1]" -c:a:0 aac -b:a 128k -ar 48000 \ -map "[a2]" -c:a:1 aac -b:a 128k -ar 48000 \ -bf 0 -g 30 -keyint_min 30 -r 30 -sc_threshold 0 \ -f hls -hls_time 3 -hls_list_size 20 -hls_flags delete_segments+independent_segments \ -hls_delete_threshold 10 \ -hls_segment_filename "/mnt/hls/%v/seg_%03d.ts" \ -master_pl_name master.m3u8 \ -var_stream_map "v:0,a:0,name:360p v:1,a:1,name:720p" \ "/mnt/hls/%v/index.m3u8"

最后把 /mnt/hls/master.m3u8 用 Nginx 暴露出去， 前端 hls.js 加载这个地址 —— 用户就能在 720p / 360p 之间自选或自动切换了。

多路中有一路可以直接复制，节省 CPU 算力

比如你推流时视频是 1080p 的, 在生成 1080p、720p 多路时，这其中的 1080p 就可以直接复制

ffmpeg -re -i rtsp://localhost:8554/live/source \ -filter_complex \ "[0:v]split=1[v1]; \ [v1]scale=640:360[v1out]; \ [0:a]asplit=1[a1]" \ -map 0:v -c:v:0 copy -b:v:0 2000k \ -map "[v1out]" -c:v:1 libx264 -b:v:1 1000k -maxrate:v:1 1000k -bufsize:v:1 2000k \ -map 0:a -c:a:0 copy \ -map "[a1]" -c:a:1 aac -b:a 128k -ar 48000 \ -bf 0 -g 30 -keyint_min 30 -r 30 -sc_threshold 0 \ -f hls -hls_time 3 -hls_list_size 20 -hls_flags delete_segments+independent_segments \ -hls_delete_threshold 10 \ -var_stream_map "v:0,a:0,name:720p v:1,a:1,name:360p" \ -master_pl_name master.m3u8 \ -hls_segment_filename "/mnt/hls/%v/seg_%03d.ts" \ "/mnt/hls/%v/index.m3u8"

最后把 /mnt/hls/master.m3u8 用 Nginx 暴露出去， 前端 hls.js 加载这个地址 —— 用户就能在 720p / 360p 之间自选或自动切换了。

现实提醒：copy 档的那一路的音视频参数（帧率、关键帧间隔（GOP）、禁用B帧），都要一致。 copy 档的 BANDWIDTH 参数值会不对，可以给 copy 档显式写一个 -b:v:0 2000k 解决这一问题。
